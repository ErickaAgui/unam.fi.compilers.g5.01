# JACARANDA — Final Project | UNAM FI · Compilers · Team 01

**Final deliverable:** a **C-like educational interpreter**, not a native-code compiler.
The first Jacaranda delivery was an RPLY lexer; the second used a manual recursive-descent parser and SDT. This final version replaces manual parsing with **Lark 1.3.1 (LALR)** and adds an actual execution stage.

## Quick start

Requires Python 3.10+ and `lark` (Tkinter is needed only for desktop GUI).

```bash
python -m pip install -r requirements.txt
python final_project/src/main.py final_project/examples/01_hello.c
python final_project/src/main.py final_project/examples/03_loops.c
python final_project/src/gui.py
python -m unittest discover -s final_project/tests -v
```

Expected execution from `examples/03_loops.c`:

```text
Parsing Success!
SDT Verified!

Execution output:
15
0
1
2
```

## Architecture

```text
C-like source file / Tkinter source editor
       |
       v
src/jacaranda.lark  -> Lark library lexer + LALR parser
       |                   (replaces previous manual parser)
       v
Lark parse tree
       |
       v
src/semantics.py  -> static SDT: types, variables, scopes,
       |                function existence & arguments
       v
src/engine.py     -> scoped tree-walking interpreter
       |
       v
Terminal / Tkinter output, or error with source line
```

**Previous lexer:** `src/LexicalAnalyzer.py` is retained as a historic reference. The final interpreter pipeline uses Lark's own lexer and grammar, rather than the former RPLY lexer. No LexerBridge is used. Both are parsing-library workflows allowed by the final assignment. The static SDT rules and the interpreter's evaluation rules are project code; the parser is generated by Lark.

## Supported language subset

- `int`, `float`, `double`, `bool`, `char` variable declarations, optional initialization and assignment; `void` function returns only.
- `+`, `-`, `*`, `/`, `%`, logical operations, comparisons, equality, unary signs and `!`, parentheses.
- `print(...)` and simplified `printf(...)` (string `%` formatting uses Python-style substitution).
- Functions, typed parameters, argument checks, recursion (bounded), `return`, `main` entry point.
- `if/else`, `while`, `do/while`, `for` and postfix `++`/`--`.
- Nested lexical scopes and shadowing; typed runtime values.
- Source-located syntax, semantic and runtime errors; maximum execution steps and call depth.

The interpreter executes top-level statements, then `main()` if present. Main must have no parameters. It does not interpret the full C standard, pointers, arrays, struct, standard headers, switch/goto, memory operations, or compiled binaries. The numeric semantics are intentionally simplified: `/` produces a `float`, including for integer arguments. **This is not production C compatibility.**

## Examples & testing

15 runnable `.c` files in `examples/` cover successful and failing programs. The unit test suite in `tests/test_final.py` also covers operator precedence, runtime error safety, argument checking, scope isolation, unreachable semantic errors, short-circuit evaluation, and generation of a Lark parse tree. Run unit tests before submitting.

## Project safety and limitations

The interpreter is intended only for educational C-like input; it does **not** call Python `eval` or execute arbitrary OS commands. Runaway computation is bounded by `max_steps` (default 100,000) and `max_depth` (64). It has no filesystem/network built-ins exposed to interpreted programs. Static analysis is intentionally limited and may not discover all issues, such as a non-void function that returns only on some possible paths; those cases are also checked at runtime.
